# What Totaal does for your company — and how

For companies under 100 people, and for every job in them. Each benefit names the mechanism that produces it.

## 0. One external plugin that builds yours — for the whole team
| Benefit | How |
|---|---|
| One external install, then plugins that are truly yours | Totaal is the only plugin from outside. It builds the company's own plugins: a core plugin and area plugins, from a single source of skills in the wiki. |
| A start that fits your business on day 1 | Claude asks what you sell, which functions you have and which work recurs. It then installs the right base plugins out of nine (leadership, sales, accounts, support, operations, finance, marketing, people, product), each with real starter skills. |
| Plugins that become yours through use | Base plugins are starting points. Every correction becomes a rule, and every recurring task without a skill becomes a new one. Each employee receives the updated build in their morning report. |
| Each employee gets exactly what their job needs | A personal build per person: the plugins of their role, minus the skills they refused, plus their settings. It is derived automatically from their preferences page, so nobody hand-edits a plugin and nothing gets lost. |
| Everyone benefits from everyone's improvements | A skill improved for one person is proposed to everyone concerned. Adoption is tracked per employee, from the build they actually installed. |
| Every role gets value, not only developers | People talk to Claude in plain language. Claude handles git, scripts, builds and routines. Each person connects GitHub once on day 1; after that, Claude does everything. |
| Everyone works from the same memory | Sales, support and finance read and write the same account journals, so a client never has to repeat themselves. |

## 1. Newcomers become autonomous in days
| Benefit | How |
|---|---|
| A newcomer ships real work in week 1 | The manager names a first deliverable on day 1; the newcomer starts from what the wiki already holds about the accounts and the method. |
| Colleagues stop repeating themselves | The wiki answers first. Every question it could not answer goes into a gaps register and becomes a page within the week. |
| Day 1 setup takes one hour, not two weeks | The `onboarding` skill prepares accesses, calendar, reading path and welcome message before day 1. On day 1 it installs the newcomer's Claude: personal company plugins, connectors, wiki, morning routine. |
| Nobody falls through the cracks | Check-ins run on their own at day 1, day 7 and day 30. They verify each step with the tools and report to the newcomer and the manager. |
| Onboarding improves with every hire | The day-30 review measures time to first deliverable and the share of questions the wiki answered, then proposes changes to the path. |
| Departures don't take knowledge with them | Offboarding reassigns accounts and moves anything that lived only in the person's head or personal Claude memory into the wiki. |

## 2. Knowledge compounds instead of evaporating
| Benefit | How |
|---|---|
| One source of truth for the whole company | A git-backed wiki on GitHub that Claude maintains. Every session reads it before acting and writes to it before closing (the three writes). |
| Answers you can trust | Every answer cites its sources and the date of the newest one, and warns when that date is older than 7 days. The wiki is never mistaken for proof that something didn't happen. |
| Every client has a complete memory | One card and one newest-first journal per account. Every contact named is updated in the same session. Contract-end and renewal dates are tracked separately. |
| Decisions don't get relitigated | Debated topics get a decision page with options, owner and date. Contradictions are kept side by side with their sources, never silently overwritten. |
| Meetings turn into action | Transcripts, never AI recaps, are turned into decisions, actions and risks, filed with the account. Missed recordings are caught up by comparing IDs, not time windows. |

## 3. Claude works while you don't (don't babysit Claude)
| Benefit | How |
|---|---|
| Every morning, one report with only what needs you | A cloud routine per person sweeps mail, calendar, CRM, chat, tickets and recordings. The report opens with at most 3 decisions waiting on you. |
| Tomorrow's meetings are prepared tonight | Each client meeting gets a prep page listing what is already decided, so settled topics are not reopened. |
| Tasks are proposed, not imposed | Claude recommends; you Approve, choose Later, or mark Not interested in one reply. Refusals are remembered and never proposed again. |
| Runs don't stall waiting for you | Scheduled runs never stop on a question. They decide, say which reading they took, and batch decisions into the report. |
| No laptop needs to stay awake | Routines run in the cloud. Only browser steps for tools without a connector run on a member's computer. |
| Silent failures become visible | Every zero has to be proven. A run states its totals, names the phases it lost, and ends with "what could this run have done better". |

## 4. Every tool reachable, without manual copy-paste
| Benefit | How |
|---|---|
| Maximum automation from your existing tools | The tool ladder: connector first, then API, then the browser (Claude in Chrome) when there is no connector, and a human only as a last resort. |
| Connectors actually get connected | Setup, onboarding and the daily environment check push each missing connector, with one line saying what it unlocks. |
| No more false "I can't" | Claude never says "impossible" without listing which rungs of the ladder it tried. |

## 5. The system gets better every day
| Benefit | How |
|---|---|
| A correction never has to be given twice | Inline tuning: each correction becomes one rule in the right skill, linked to the page that explains it, and included in everyone's next personal build. |
| Repeat mistakes are fixed at the root | A rule broken twice is treated as a placement problem: wrong skill loaded, rule buried, rule kept only in personal memory, or no step to reread it. |
| Your best practices become company skills | `skill-writer` turns recurring work (reports, quotes, support replies) into skills, placed in the right company plugin and shipped in everyone's personal build. |
| Everyone benefits from everyone's improvements | Improvements are proposed to every member. Adoption is tracked per person, and each choice is remembered so nothing is asked twice. |

## 6. A team that runs smoothly
| Benefit | How |
|---|---|
| Safe parallel work, even with many routines | Team mode gives every run its own branch. One daily arbitration merges the branches by meaning, deduplicates, flags contradictions and lints. |
| Clear midday focus | The midday check shows what was done (with proof), promises not kept, and what must close today. |
| Continuous improvement without blame | A review every two weeks: completion score of past decisions, DESC improvement areas, and new decisions with an owner and a deadline. |
| Clearer communication | Shared writing rules, length caps by text type, and a register of rejected phrasings that is reread before every delivery. |
| Only admins change the shared truth (optional) | In team mode, a GitHub rule lets each member write only on their own branch. Only admins, through the daily arbitration, can change `main`. |
| Sensitive things stay out | No personal data about colleagues, HR matters, named evaluations or secret values in the wiki. The arbitration removes them if they slip in. |
